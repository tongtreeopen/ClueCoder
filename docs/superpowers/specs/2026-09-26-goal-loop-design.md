# TraceCoder 显式 Goal Loop 架构设计

> 历史记录：本文对应当时的设计或验证源码快照，当前代码位于 cluecoder/；历史 revision、哈希及产物路径保留原始 CoreCoder 身份。当前用法以 README 和 CLI 帮助为准；历史成绩不代表当前版本。

日期：2026-09-26。状态：设计已获用户确认；已在当前 TraceCoder 工作树实施，实际入口与验证边界见[机制对照](../../learn-claude-code-mechanism-comparison.md)和实施计划（归档材料未收录于此副本）。

## 目标、范围与完成定义

用户要在 TraceCoder 中补入 learn-claude-code `s17_goal_loop` 的核心机制：模型提出最终回答时，由独立完成门检查目标、测试证据、预算和阻碍；未完成且仍可行动时，继续同一 Agent 循环。用户明确选择**仅在显式设置 `/goal` 时启用**。普通对话、无 Goal 的 `-p`、直接构造的 Python `Agent` 保持现有停止语义。

本阶段成功的定义是：有 Goal 的编码任务不能仅凭模型无工具调用或自称完成而自动成功；可验证命令的真实结果和来源事件必须与验收条件对应；失败、缺证、超预算或评估错误都不能冒充成功。未完成任务能恢复状态，自动续跑有硬上限，候选答案在验收前不向用户显示。目标不是自动生成测试、保证测试覆盖充分，也不是自进化 Harness。

对照来源固定为 learn-claude-code 提交 [`0dcafa2` 的 s17 README](https://github.com/shareAI-lab/learn-claude-code/blob/0dcafa2ae053a1ddd6a72f265431104b08a5aa13/s17_goal_loop/README.md) 与 [`code.py`](https://github.com/shareAI-lab/learn-claude-code/blob/0dcafa2ae053a1ddd6a72f265431104b08a5aa13/s17_goal_loop/code.py)。教学实现以无 `tool_use` 为停止提议，由独立无工具模型评估；未达标时把反馈送回循环，错误和上限交还用户。其评估仍是模型判断，不是形式化验证。TraceCoder 不复制教学实现的 shell、权限或会话格式。

## 现状与方案选择

当前 [`Agent.chat`](https://github.com/tongtreeopen/ClueCoder/blob/f48ffef08762212d4f080b18442c963d35fdc339/tracecoder/agent.py) 在模型不再调用工具时立即追加助手消息、设置 `last_turn_completed` 并返回。`WorkStateStore` 已有会话工作卡、阻碍、验收条件及 Bash 命令与工具结果事件的对应检查，但完成门只有显式调用 `work_update(complete=true)` 或 `/work confirm` 才运行；普通最终回答不会经过它。CLI 的回复会流式显示，因而不能在显示后再驳回。`SessionJournal` 可记录带序号的持久事件，`ContextAssembler` 负责模型视图，MemoryCLI 在已完成回合后排入记忆提取。

考虑三种接法：

1. **推荐：在 `Agent.chat` 的唯一无工具返回点插入可选 Stop Gate。** CLI 负责装配会话级 `GoalController`，核心循环只调用统一决策接口；无控制器时原样返回。这样仍由同一循环执行工具，不需要伪造用户回合。
2. CLI 外层反复调用 `Agent.chat`。改动较小，但容易把评估反馈作为假用户发言写进会话和长期记忆，且上一份候选答案可能已流式显示，不采用。
3. 先移植完整 `s16` 工作流运行时。可复用编排概念，但为单一停止门引入过大范围，不采用。

## 命令与状态所有权

`/goal <目标>` 是唯一启用入口：在 REPL 中设置会话级目标并立即作为当前请求执行；一次性模式使用 `-p "/goal <目标>"`。`/goal` 显示目标、证据、预算与最近评估理由；`/goal off` 取消自动续跑但不删除工作卡、会话日志或文件改动。再次 `/goal <目标>` 视为显式替换：旧目标记录为已替换，新目标从零计数；工作卡产生新修订，清空旧目标的 Todo、验收项、阻碍和证据，旧卡历史仍在日志中。`--resume` 恢复当前目标及其预算；`/reset` 开始新会话，旧 Goal 留在原会话供恢复。

`GoalController` 拥有目标条件、状态、预算累计、候选答案 ID、最近理由和 Stop 决策，不拥有工具、权限或工作区。状态至少区分 `active`、`achieved`、`needs_user`、`limit`、`failed`、`error`、`cancelled`：只有 `achieved` 可作为自动成功；`needs_user`、`limit` 和 `error` 保留目标条件，允许用户查看、补充信息、继续或关闭。`failed` 表示证据证明目标不可完成，不等于成功。工作卡仍负责当前步骤、Todo、验收条件和证据；Goal 是会话的自动续跑控制器，不把项目 `TaskStore` 的 `completed` 当作 Goal 成功。

首版只在严格 CLI 根会话装配 Goal。子 Agent 的文本不能直接结束根 Goal；Python API 未装配控制器时保持兼容。Plan Mode 下 Goal 状态可查询，也可设置目标，但不立即执行或自动续跑；用户批准退出 Plan Mode 后才开始。MCP 与命令 Hook 不因 Goal 而重新启用，`--yes` 仍只影响原有工具许可。

## Stop 决策与证据门

有活动 Goal 时，CLI 不把生成中的文本直接流式展示为最终结论；工具调用提示可以照常展示。模型一次无工具响应是**候选停止**，先持久化候选和用量，再进行以下顺序的只读判断：

1. **确定性门。** 读取工作卡与会话事件，检查未解除阻碍、已登记验收项、实际工具调用的命令及对应结果。首版不做自动意图分类：所有 `/goal` 都必须有至少一项可核验的检查结果，或用户明确 `/work confirm`，否则不能自动通过；助手文本、Todo 全完成、未执行的命令、失败/中断/被拒的工具结果都不是成功证据。验收命令之后发生 `write_file`、`edit_file` 或 Bash 调用时，先按证据可能过期处理，要求重新验证；这是保守规则，不声称能识别所有外部文件变动。主观条件需要用户明确确认，不能由评估模型单独批准。
2. **预算门。** 默认最多 3 次自动驳回后续跑、累计自动执行 15 分钟、累计已报告 30,000 token，并保留 Agent 原有每次请求轮数上限。工作模型与评估模型的已报告 token 都计入；部分提供方不返回用量，此时不得宣称 token 上限得到严格执行，时间和续跑次数仍是硬上限。暂停/退出 CLI 的时间不计入累计自动执行时间；预算与次数持久化，重启不重置。价格估算不作为硬预算。
3. **独立评估。** 前两门未阻断时，使用单独的无工具模型调用，输入有界目标、候选答案和带事件 ID 的证据摘要，输出严格结构化 `ok`、`reason`、`impossible` 与引用的证据 ID。只接受真实存在、类型正确的引用；评估模型不能运行命令、修改状态、覆盖确定性失败或解释权限拒绝为成功。它可因目标语义与测试不相符而驳回，不能保证发现所有弱测试。

若仍可行动，控制器记录理由并从同一 Agent 循环继续；反馈放进有界的 Goal 上下文区，**不伪装成真实用户消息**，也不作为长期记忆的用户直接证据。达到硬上限、权限被拒且需要用户决定、目标不可行或评估器出错时停止自动续跑，显示可操作状态与候选答案的“未验收”标记；不设置自动成功。最终成功时才显示已验收答案，并将工作卡按其既有证据规则归档。用户显式确认仍可完成主观项，但该确认有独立事件来源，不是评估模型的自我认证。一次性模式仅在 `achieved` 时退出码为零，其他 Goal 终态返回非零并打印状态；无 Goal 的退出码保持原状。

## 持久化、恢复与失败语义

Goal 事件写入同一 `SessionJournal`：设置/替换/关闭、候选停止、评估结果、证据引用、预算增量和终态都有顺序及版本。恢复时从事件重建状态、已用续跑次数和累计活跃时间；不从模型视图或 LLM 进程内计数推断。进程运行期间严格检查 15 分钟上限；异常退出时只能按最后已落盘事件重建活跃片段，无法精确计入最后未落盘的时间，恢复后必须由用户显式触发继续，且次数上限仍有效。日志写入失败不得继续下一次模型请求，也不得宣称可恢复。

若候选答案已持久化而评估未完成，恢复时只重新评估该候选或返回待评估状态，不自动重放此前工具。若评估结果已得出但持久化失败，停止自动续跑并报告状态不确定，不能把未持久化决策当成成功。崩溃前已经执行的工具副作用不因 Goal 恢复而自动重跑；工具结果缺失沿用 SessionJournal 的“不确定”标记。评估失败保留目标与理由，允许后续用户输入触发重试；不得无限自动重试。

Goal 自产生的反馈与状态事件不进入长期记忆的“用户原文”安全自动保存路径。MemoryCLI 只有在 Goal 达成或明确交还用户的终态后处理本轮，不因被驳回的候选文本就提取“已完成”记忆。无 Goal 的会话、已有记忆和旧会话格式仍按原行为读取。

## 验证与明确不做的事

先用脚本 LLM 与真实临时文件系统测试：无 Goal 时行为不变；`/goal` 设定后立即执行；候选答案不提前显示；真实通过/失败/缺失/过期的 Bash 证据；阻碍、主观条件、权限拒绝、Plan Mode；独立评估器返回通过/未过/不可行/格式错误/异常；3 次续跑、时间及已报告 token 上限；中断与 `--resume` 后预算不重置且不重放工具；`/reset` 保留旧 Goal；Goal 反馈不能成为自动长期记忆来源；REPL、`-p`、`--yes`、`--resume` 与严格 demo 不回归。最终运行全量 pytest、Ruff、compileall 和差异检查；真实模型的评估准确率需单独报告，不以离线测试代替。

不在本阶段实现 s11 后台任务的 `defer`/通知续跑、s16 通用工作流、团队协作、自动选测试、强跨进程事务或候选策略晋升。若后来引入后台任务，Goal 的 `needs_user`/等待状态须由宿主统一事件机制唤醒，而不是在 Goal Controller 内另造命令队列。实现时更新 `docs/learn-claude-code-mechanism-comparison.md`：记录 s17 源码入口、TraceCoder 的 Stop Gate 与工作卡整合、流式输出与恢复差异、测试证据及未验证边界；规划本文不能写成已实现。
