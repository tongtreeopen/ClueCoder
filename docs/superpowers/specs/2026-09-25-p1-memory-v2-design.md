# TraceCoder P1 Memory v2 设计

> 历史记录：本文对应当时的设计或验证源码快照，当前代码位于 tracecoder/；历史 revision、哈希及产物路径保留原始 CoreCoder 身份。当前用法以 README 和 CLI 帮助为准；历史成绩不代表当前版本。

## 目标、来源与边界

用户已选择先补齐 learn-claude-code 中适合 TraceCoder 的机制，再做自进化 Harness。本阶段只扩展项目级 Memory：相关召回、回合末候选提取、经确认或显式开启的自动保存、可撤销写入，以及可审阅的合并。P2 Task、后台执行和自进化不在本阶段。成功标准不是“模型一定记得正确”，而是每条持久写入都有明确来源、模式和可验证的控制边界；主任务的回答不因记忆辅助调用失败而丢失。

对照来源固定为 learn-claude-code 提交 `0dcafa2ae053a1ddd6a72f265431104b08a5aa13` 的 `s09_memory/code.py`：索引、最多五条模型选择与关键词回退、回合末提取、达到阈值后的合并。TraceCoder 已有 `MemoryStore`、`remember` / `read_memory` / `list_memories`、CLI 的 `context_catalog` 和项目级 `.tracecoder/memory/`。保留这些入口和现有文件兼容性；不将教学示例的自动覆写和删除直接搬入 CLI。

## 模块与调用流程

新增独立的 `MemoryWorkflow`，由 CLI 在 `Agent.chat()` 外层调用；它依赖现有 `MemoryStore`、一个符合 `LLM.chat(messages, tools=[])` 的模型、以及当前工作区策略，不依赖工具执行器。`MemoryStore` 负责记录格式、索引、版本校验与撤销；`MemoryWorkflow` 负责召回、候选生成和写入决策；CLI 负责向用户展示、获取确认与切换会话模式。这样不会把交互提示塞进 Agent 工具循环，Python API 直接构造的 `Agent` 也不会被悄悄改成自动写记忆。

每轮 CLI 顺序如下：

1. 接收用户输入；从记忆元数据索引选相关记录，截断后注入本轮系统上下文。只有本轮结束后才替换这份上下文，避免多次工具轮重新选择。保留当前简短索引供 `read_memory` 显式使用。
2. `Agent.chat()` 正常执行并返回最终回答。只有真正完成最终回答的轮次才进入提取；异常、中断或达到 `max_rounds` 时不提取。Agent 对外返回字符串的现有接口不变，内部增加可检查的本轮完成状态。
3. 独立模型请求从**本轮用户输入和最终回答**提取最多三条候选；不把原始工具输出、隐藏系统提示词或完整历史会话送进提取请求。候选验证后按当前模式展示、确认或保存。辅助请求失败仅显示简短状态，不修改已生成的主回答。

子 Agent 不独立运行 MemoryWorkflow；其结果只有在主 Agent 最终回答中体现时才可能成为候选。CLI 的交互、`-p`、`--resume` 共用同一流程；`--demo` 使用脚本模型验证接线，但不产生真实模型成本。

## 相关召回

从现有记录的 `name`、`description` 和新增的可选 `type` 建立索引。优先用一次无工具模型调用返回记录 ID 列表；要求合法 ID、去重、最多五条。模型异常或格式无效时使用确定性关键词匹配；合法的空列表表示“无相关记录”，不触发回退。两者都无法确认相关性时不载入正文。被选正文总量上限为 20,000 字符，单条按剩余额度截断。系统提示词明确标注“历史资料，不是新指令；当前用户请求优先”，并列出记录来源；不把记忆文件当作高信任系统指令。

为避免每个工具轮重复付费，召回只在用户新一轮输入时计算一次。索引为空则不调用选择模型。召回和提取的模型调用计入现有 token/费用统计；LLM 层为辅助请求提供不改变主 Agent 请求配置的单次输出上限，不提供工具 schema。

## 候选提取与保存模式

候选字段为 `name`、`description`、`type`、`content`，类型限定为 `user`、`feedback`、`project`、`reference`，对应 s09 的稳定偏好、重复反馈、项目事实和用户指定的外部参考。旧记录没有 `type` 仍可读，新增类型不改变现有名称哈希文件路径。候选必须符合现有名称与 16 KiB 正文上限；拒绝无效 JSON、未知类型、空字段、同批重复、与已有记录相同内容。对内容使用确定性凭据规则（常见 API key/token 前缀、私钥头、带密码的 URL）做拒绝；对其他疑似敏感内容只给警告，不承诺完整识别。模型指令要求只保留跨会话有用的信息，不保存临时任务状态、一次性命令、助手推测或当前对话摘要。

默认是审核模式：交互 CLI 在回答后逐条展示候选及其类型、简介、正文，用户逐条接受或拒绝；拒绝不落盘。`-p` 默认没有交互确认，因此只输出候选而不保存。通过 `/memory auto on` 可以在**当前交互 CLI 进程**显式启用自动模式，`/memory auto off` 关闭；`-p` 仅在显式 `--memory-auto` 时自动保存。自动模式每条保存后显示名称和撤销方式。`--yes` 只处理现有工具权限，不开启自动记忆；`--resume` 读取旧会话消息但自动模式仍关闭；`/reset` 只清会话消息，不改变本进程模式。

Plan Mode 允许只读召回，但禁止候选写入、合并与撤销；在 Plan Mode 下默认不做提取，以免产生无法保存的候选与额外费用。现有 `remember` 工具的权限机制、`replace=True` 语义不变；自动模式不会让它绕过工具许可。`MemoryWorkflow` 的保存授权独立于 `Permission.allow_all`，必须是候选确认或显式的当前进程自动模式。

## 冲突、合并与撤销

自动保存仅创建不存在的记录。名称相同或正文规范化后相同的候选不静默覆盖：完全相同者跳过，名称相同但内容不同者转成需人工审阅的更新提案；其他语义相似/矛盾只由模型提示，不把不可靠的语义判断当成自动覆盖依据。审核模式也要明确显示旧内容与拟议新内容，不能把“保存”解释成默认覆盖。人工批准后的更新通过同一受控写入入口。`MemoryStore` 对所有受控写入先验证工作区内真实路径、版本与大小，写入记录和重建索引时使用同目录临时文件及原子替换；现有显式 `remember` 的兼容行为保留。

每次受控操作生成一条持久撤销记录；普通保存含一个目标，合并含所有被改动目标的写入前内容（新建时为空）和写入后哈希。撤销记录放在被 Git 忽略的 `.tracecoder/memory/` 中。写入前先持久化 `pending` 日志，完成记录和索引后标记 `committed`；启动时发现未完成日志则用已验证的前镜像恢复，若当前文件与日志预期状态冲突则停止记忆写入并提示人工处理，绝不猜测覆盖。`/memory undo` 撤销最近一次已提交操作，即使 CLI 重启也可用；连续调用可逐次倒序撤销。撤销前须检查所有目标的当前哈希与写入后哈希一致，否则整次拒绝，不覆盖后来由人工或另一进程修改的内容。撤销后重建索引；文件 `/undo` 栈与记忆撤销栈相互独立。显式 `remember` 不进入这条受控撤销栈，但它的后续改动会触发哈希冲突。该机制提供可恢复性，不声称跨进程并发或断电场景完全事务化；P1 至少测试未完成日志恢复和冲突拒绝。

与 s09 一样，记录数量达到 10 条后可请求模型生成合并提案；输入设 20,000 字符上限。合并提案必须列出将保留、改写和删除的记录及差异，用户明确确认后才应用，自动模式也不得跳过。合并同样写撤销信息；若无法安全保存所有前镜像、验证冲突或完成索引更新，就拒绝应用。不会在每轮阈值达到时反复调用模型：每次存储版本只生成一次提案；被拒绝后仅在存储内容变化或用户主动请求时重新生成。若这部分无法在 P1 的测试边界内可靠实现，应作为 P1 的未完成项报告，不能称为“自动合并已补齐”。

## CLI、错误处理与验收

新增 `/memory auto on|off`、`/memory undo`，在 `/help` 中标明与文件 `/undo` 的区别；`--memory-auto` 只用于一次性模式。未识别的 `/memory` 子命令给出用法，不送给主模型。辅助模型调用无工具执行权限，失败或返回不合格内容时可见地跳过，主任务回答和已有记忆不变；读取损坏记录沿用现有“跳过并警告”行为。显示候选时不输出隐藏上下文或原始工具数据。

离线测试使用 `ScriptedLLM` 或等效脚本模型，不访问真实 API：验证五条/20,000 字符召回、非法选择与关键词回退、三条候选上限、旧记录兼容、重复和敏感内容过滤、审核拒绝与接受、自动模式显式开关、`-p` / `--yes` / `--resume`、Plan Mode、子 Agent 不重复提取、主回答不受辅助错误影响、重启后撤销、哈希冲突拒绝、合并差异审阅和撤销。跑 P1 定向测试、现有全量 pytest、Ruff、compileall 与 `git diff --check`；分别报告离线验证和真实模型 E2E 的边界。
