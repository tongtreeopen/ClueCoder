## 2. 真实 CLI

cli_checks.py（归档材料未收录于此副本） 使用真实 `python -m tracecoder` 子进程、Windows 伪终端、当前模型和 Docker；没有替换模型、工具或 prompt 函数。子进程 USERPROFILE 与工作区放在独立临时目录，交互测试关闭 Memory extraction，凭据只经子进程环境传入。

三种一次性模式通过：`--yes -p '/goal ...'` 成功为 exit 0 / achieved；故意失败为 exit 1 / needs_user；无 Goal 的后台启动后立即返回，退出时真实取消且清理成功，未隐式开启 Goal。原始记录：成功（归档材料未收录于此副本）、失败（归档材料未收录于此副本）、普通退出（归档材料未收录于此副本）。

实际 CLI 发现评测模式的 GoalEvaluator 以前创建了单独的未计数模型；现在评测模式共用 BudgetedModel，工作及评估请求都受同一预算计数。普通模式保持原接口。另外 `/help` 的旧 30k 文本同步为 100k。

交互原始记录见 cli-repl.json（归档材料未收录于此副本）。驱动探索失败全部保留为 cli-repl-*-failed.json：一次批量写入文字及 Enter 被 prompt_toolkit 识别为粘贴，需要分开发送；初次观察器还误依赖多个会话文件的枚举顺序。修正驱动，没有把模拟直接调用 `_repl` 当作真实终端通过。无模型的 pty_probe.py（归档材料未收录于此副本） 验证输入提交方式；console_input.py 只对显式给定的本次测试 CLI PID 发出控制信号。

最终真实交互检查点 **7/7**：Goal 实际 achieved、`/goal` 显示 100000 预算、reset 创建新会话、活跃后台命令经 reset 真实取消、Ctrl+C 返回 REPL、quit 正常退出、所有后台结果的清理验证成功。与三种一次性模式合计四组 CLI 场景均通过。交互模式用量没有外部统一封顶统计，不能合并进八场低指导的调用/token 总量。

## 3. 长会话与压缩

long_context.py（归档材料未收录于此副本） 构造 12 次用户更正后 120 个完整工具调用/结果对。修复前压缩后仍估算 30597 token，超过 12400 输入预算，见 红色探针（归档材料未收录于此副本）。原因是当前请求位于保留前缀与尾部之间时，把尾部扩回当前请求，连带保留了整段工具历史。

现在保留当前用户请求所在前缀、裁掉中间历史、保留配对尾部，再归档旧输出；同一探针变为 **9311/12400 tokens**，当前要求和调用/结果配对均保留。强制摘要仍保留最新更正；过大的当前请求明确报错，不能静默截断。真实 Docker 先检查通过，实际 edit_file 后旧事件被拒绝，压缩不能恢复其有效性，再跑原命令后只接受新事件。结果（归档材料未收录于此副本）四项通过。

其中摘要和历史结构使用记录数据的确定性探针，证据新鲜度部分使用真实 Docker；没有声称验证任意长会话的模型语义准确率。

## 4. 无进展重复调用提示

[`Agent._repeat_feedback`](../../tracecoder/agent.py) 在当前用户回合内核对最近三个工具结果：工具名称、规范化参数和真实结果 SHA-256 都相同，且为列出的只读工具时，在下一请求中提示无进展，建议使用已有结果、改变下一步或有界等待。修改、结果变化、工具变化和新用户消息自然重置判断；Bash 重检不属于该只读检测，必要检查不被阻断。

这只是一条可验证的提示，不增加停机阈值、默认自动续跑或新的权限。超过预算仍沿用既有停止门。先红后绿记录及四项回归见 repeat-red.txt（归档材料未收录于此副本）、[test_repeat_feedback.py](../../tests/test_repeat_feedback.py)。真实模型探针实际执行三次文件读取，下一请求收到提示后结束，共 2 次模型请求、2353 token，见 repeat-live.json（归档材料未收录于此副本）。单个受控探针不能证明任意循环都能被模型终止。

低指导还复现两个请求协议问题：同一回合候选没有 reasoning 正文时，DeepSeek 仍要求显式 reasoning_content 字段；只在官方端点带工具的请求视图补空字符串，保留已有内容，不修改持久历史。实际请求 红（归档材料未收录于此副本） / 绿（归档材料未收录于此副本）通过。工作回复仅有思考且无正文/工具时，现在记录 goal_worker_output、计入 usage、明确停止，绝不把无效消息追加进后续请求。对应回归先失败后通过。

## 5. 异常退出与清理范围

crash_cleanup.py（归档材料未收录于此副本） 两次强杀实际 CLI 进程：本次背景检查由容器内 watchdog 在 timeout=6 后退出，ExitCode=124。复用现有独立 Runner 的 `_cleanup_workers`，列出精确 run label、移除前再次核对 label、移除后验证；两次均成功。另一 run 的哨兵容器在清理后仍运行，无效 run ID 被拒绝。结果（归档材料未收录于此副本） **2/2**。

首次全量回归 **518 passed, 1 failed**：已有中断测试断言所有 tracecoder-sandbox 容器都不存在，把并行测评的外部容器错误计入失败。测试 fixture 现在使用独立 run ID，四个容器断言核查该 fixture 的精确 label，保持检查范围和其他任务隔离；原失败日志保留。没有新增后台守护服务或普通 CLI 自动清理未知历史容器。强杀后可用既有外部 Runner 回收自己的容器；普通 CLI 的异常断电自动恢复仍未实现。
