# TraceCoder 预算感知上下文设计

> 历史记录：本文对应当时的设计或验证源码快照，当前代码位于 cluecoder/；历史 revision、哈希及产物路径保留原始 CoreCoder 身份。当前用法以 README 和 CLI 帮助为准；历史成绩不代表当前版本。

日期：2026-09-29。状态：已实现；真实容器和模型评测未验证。实现证据见实施计划（归档材料未收录于此副本）。

## 目标与范围

把 TraceCoder 当前的 `ContextAssembler`（选择每轮模型视图）和 `ContextManager`（压缩消息历史）收敛为一条可预测的请求前流程，并吸收 learn-claude-code `s08_context_compact` / `s15_integrated_harness` 的完整工具输出归档、保留近期结果和 prompt-too-long 恢复。

主要目标是在 SWE 类长任务中降低重复发送历史的成本，同时保留原始会话证据、支持按需恢复，且不丢当前用户请求和未消费工具结果的调用/结果记录。超长结果可外置全文，但模型视图必须保留其结果块、预览和归档引用。单次请求上下文和整题累计用量是两个独立预算。

本阶段不改变普通 Agent 的工具权限、Goal Stop Gate、记忆提取语义或模型协议；不承诺仅靠压缩解决 Agent 过度探索，也不把 `ready_for_grade` 当作修复成功。

## 当前状态与方案选择

当前 `Agent.chat()` 在收到用户消息后、工具返回后调用 `ContextManager.maybe_compress()`。严格 CLI 的 `_full_messages()` 则调用 `ContextAssembler.build()`，通常只装配近期消息、工作卡、导航和索引。前者对完整 `Agent.messages` 估算 token，后者对即将发送的视图另行裁剪；可能为下一次本来不会发送的旧消息额外调用摘要模型。`SessionJournal` 保存会话事件，但超过 64 KiB 的消息会截断正文；`read_session_event` 目前只读取事件 JSON，不能跟随完整输出归档。

考虑三种方案：

1. **只给 ContextManager 加归档和超限重试。**改动少，但仍由两处分别组装与压缩，无法消除重复判断。
2. **只用 ContextAssembler 的近期窗口与按需读取。**每轮简单省 token，但遇到超长当前轮次或大工具结果时缺少渐进压缩和服务端超限恢复。
3. **推荐：让 ContextAssembler 成为每次请求的唯一入口，并复用 ContextManager 的压缩能力。**所有预算决策基于最终模型请求视图；SessionJournal 保持可恢复记录，工具输出归档在超限时提供完整原文读取。

## 请求预算与阈值

设 `M` 为模型上下文窗口与 TraceCoder `max_context_tokens` 的较小值，`O` 为本次请求的最大输出 token，安全余量 `S = 10% * M`。可用于输入的预算为 `B = M - O - S`。这些量按当前模型与请求计算，不把 learn-claude-code 的字符数阈值直接换算成 token。

以 `M=128,000`、`O=4,096` 为例，`B` 约为 `111,104` tokens：

- 目标长度 `T = 70% * B`，约 `77,773` tokens。低于此值不做历史摘要。
- 超过 `T`：执行低成本缩减，直到回到 `T` 以下或没有可缩减项。
- 超过 `85% * B`，约 `94,438` tokens：允许摘要旧轮次。
- 超过 `95% * B`，约 `105,549` tokens：紧急视图只保留当前请求、活动工作卡、最近完整工具交互及一个旧历史摘要。
- 超过 `B` 且仍无法缩减：在模型调用前返回明确的上下文预算错误，不静默截断当前请求。

本地估算须覆盖最终 system 消息、工具 schema 和消息体。记录每次提供方报告的 `prompt_tokens`；同一模型有近期真实用量时用它校准估算系数，新会话或用量缺失时继续使用保守安全余量。未知模型窗口不能被当成已验证的 128K；应采用显式配置上限并在元数据中记录该上限来源。

## 每次模型请求的数据流

1. `ContextAssembler` 从 Agent 消息、工作卡、Goal 反馈、会话日志和索引构造一个候选请求。当前用户请求和当前轮次从最近一条用户消息开始保留；工具调用与对应工具结果必须作为一组保留。
2. 组装优先级从高到低为：系统与安全指令、当前用户请求、活动工作卡、当前轮次及最近完整工具交互、旧历史摘要和事件导航、Skill/Memory 索引。压缩不得删掉更高优先级内容来保留更低优先级索引。
3. 估算候选请求 token。低于 `T` 时直接发送；超过时按下述顺序处理，并在每一步后重新估算同一个候选请求。
4. 最终只从此入口调用模型。移除现有在用户消息追加后、工具结果追加后对整段原始历史单独压缩的重复决策；如有 `/compact`，它显式请求同一流水线压缩当前模型视图。

## 压缩顺序与归档

把 learn-claude-code s08 的四步保留为可辨认的顺序，但用 TraceCoder 的 token 预算和 SessionJournal 事件索引替代独立字符窗口与重复 transcript：

1. **`tool_result_budget`：归档当前工具结果批次。**若当前批次合计超过 200,000 字符，从最大结果开始外置；单个结果超过 30,000 字符时全文先脱敏后保存，模型视图保留约 2,000 字符预览及归档引用。若批次未超总量，留到后续 `fit_tool_results` 判断是否需要外置。未消费结果仍保留 tool-result 块及预览/引用。
2. **`snip_compact`：限制消息数量。**当候选消息视图超过 50 条时，保留开头 3 条和最近 46 条，其余中间消息由事件范围标记代替。边界向外移动以保留 assistant tool call 与对应 tool result。原始事件已由 SessionJournal 保存，因此引用其事件 ID 范围，不另写一份重复 transcript。此步骤按消息数触发，即使 token 数还低于 `T` 也执行。
3. **`micro_compact` / `fit_tool_results`：缩短工具结果。**当估算 token 超过目标 `T` 时，先把已被模型消费的较旧工具结果换成归档引用，最近 3 个已消费结果尽量保留原文；若超长当前结果仍导致超预算，再从最大结果开始外置并保留预览和引用。全程不拆工具调用/结果配对。
4. **`compact_history`：最后才总结旧历史。**低成本缩减后仍超过 `85% * B` 时，保存旧事件范围并生成一次有界摘要。摘要覆盖目标、用户约束、决策、已改文件、验证结果、错误和剩余工作；它是低信任导航信息，不是授权或验证证据。摘要只覆盖尚未总结的新事件范围。

超过 `T` 是开始低成本压缩的软阈值；完成前三步后若仍高于 `T`、但没有更多可缩减项且低于 `85% * B`，允许本次请求发送，不为追求目标长度额外付出摘要调用。到 `95% * B` 时进入紧急视图，只保留当前请求、工作卡、最近完整工具交互和最近摘要。超过 `B` 仍无法缩减，则在调用模型前返回明确错误，不静默截断当前请求。

收到提供方明确的 prompt-too-long 错误时，额外执行一次 **`reactive_compact`** 并重试一次；这是请求失败后的恢复路径，不属于上述四步。显式 `/compact` 与 learn-claude-code 的 compact tool 一样，是用户主动触发 `compact_history` 的入口；日常自动压缩仍在每次模型请求前执行。第二次仍失败则交还用户，不循环重试。

归档内容先经过现有脱敏规则，再完整保存到当前 session 的归档目录，事件中记录稳定引用、字节数和 SHA-256。SessionJournal 只保存可读预览和归档引用，避免其 64 KiB 限制造成无提示丢失。已有 `search_session` 用于查找事件，`read_session_event` 扩展为对归档引用做有界读取；返回内容仍标为不可信历史数据。摘要保存来源事件范围；新增事件不使同一旧范围反复触发摘要调用。

## 整题累计预算提示

该策略只在评测 Harness 显式提供累计 token 上限并可读工作区 diff 时启用，不改变普通聊天行为。使用提供方真实 `prompt_tokens + completion_tokens` 累加；用量未知时标记 unknown，不用估算值伪装精确预算。

- 累计预算达到 60%，且工作区还没有生产代码改动：给 Agent 一次简短进度检查，要求总结已有证据、指出候选文件，并优先形成最小补丁。
- 达到 80%：提示停止宽泛探索，优先改动已有最高置信度的实现并执行定向验证。
- 这是指令提示，不禁止用户请求的工具，也不把“有 diff”作为质量成功；官方 Gate 仍是修复结果判定。

此策略不属于上下文压缩本身。压缩降低后续请求重复发送的历史成本；累计预算提示针对没有产出的长时间探索，两者分别记录指标。

## 失败语义与兼容

- 归档写入、校验或日志持久化失败时，不得把内容替换为不可恢复引用；保留原请求或停止调用并报告错误。
- 摘要模型失败时回退到现有确定性关键信息提取；若提取也不可用，保留原文或使用事件导航，不把空摘要当成功。
- 最近工具对、当前请求和工具调用 ID 配对始终完整；恢复旧会话时，引用必须通过 session 根目录路径校验，不能读取工作区外的任意路径。
- 无提供方 usage 时继续使用保守估算进行单次请求预检，但整题累计预算状态显示 unknown。
- 新版 session 可读取归档引用；旧 session 的已截断内容无法重建，继续按其现有事件内容读取，不假装原文仍存在。
- Python API 直接构造 Agent、无严格 CLI ContextAssembler 的路径，应继续使用现有 ContextManager 行为或显式配置同一入口；实现计划须明确其覆盖面，不能宣称所有调用方式均已受预算控制，除非接口确实接线。

## 验收与评测

离线验证至少覆盖：预算公式与阶段阈值；不同模型窗口和输出预留；低优先级内容先移除；工具调用/结果配对；最近 3 条已消费结果保留；大结果归档、脱敏、哈希和有界回读；同一事件范围不重复摘要；当前请求不能被丢弃；摘要失败回退；prompt-too-long 最多重试一次；旧 session 可读取；usage 缺失时状态明确；累计预算提示只在评测模式生效。

先以一条真实模型任务确认 prompt usage、归档读取和重试路径，再在固定的内部回归任务上做对照：任务快照、模型/参数、输出预算和累计预算保持一致，只改变上下文流水线。记录独立 Gate 通过数、每任务累计 token、prompt token 中位数、首次生产代码改动前 token、无生产改动比例、归档读取次数、摘要调用次数和失败原因。该结果用于内部迭代，不代表外部仓库修复能力。

本方案不预设成功率提升；只有对照结果显示 token 降低且官方 Gate 质量未退化，才接受该机制。若效率改善但修复质量下降，调整优先级或摘要策略后重测。
