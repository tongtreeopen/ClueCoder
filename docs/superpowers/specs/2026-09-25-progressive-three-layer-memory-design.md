# TraceCoder 渐进式三层记忆架构设计

> 历史记录：本文对应当时的设计或验证源码快照，当前代码位于 cluecoder/；历史 revision、哈希及产物路径保留原始 CoreCoder 身份。当前用法以 README 和 CLI 帮助为准；历史成绩不代表当前版本。

日期：2026-09-25。状态：用户已确认；本文是设计，不代表功能已实现。

## 目标与设计判断

用户要求 TraceCoder 同时具备长期记忆、短期记忆和工作记忆，并以渐进式披露控制上下文。这里的“三层”表示**用途和生命周期**，不是三个互相搬运文本的存储桶：

| 使用层 | 应回答的问题 | 权威数据 | 默认给模型的内容 | 结束条件 |
| --- | --- | --- | --- | --- |
| 工作记忆 | 当前要做什么、做到哪里、凭什么算完成？ | 会话关联的工作卡及验收证据 | 一张有界的活动卡 | 有证据地完成后从活动上下文归档，不删除审计记录 |
| 短期记忆 | 本次会话发生过什么、如何恢复？ | 可恢复的会话事件记录 | 最近回合与已压缩摘要 | 会话结束仍可恢复；压缩只改模型视图，不改原始记录 |
| 长期记忆 | 跨会话仍有用的用户偏好、反馈和项目事实是什么？ | 带来源、作用域、版本的记忆记录 | 有界索引；相关条目按需展开 | 更正、撤销或显式删除；不随单次任务完成消失 |

项目规则、Skill、工具权限和安全策略不属于模型自提炼的长期记忆；其优先级不能被召回内容覆盖。已有 `TaskStore` 是项目任务清单，不能直接充当当前会话的工作卡；Todo 全勾选也不等于目标验收。

目标是：不再每轮询问是否保留、未完成任务可恢复、完成判断有证据、上下文按需披露，并在异常或压缩后仍能追溯来源。首版采用文件存储和确定性索引，不引入向量库、常驻后台服务或自进化评估器。

## 当前实现与迁移边界

当前 `tracecoder/cli_memory.py` 在 CLI 正常回合后调用 `MemoryWorkflow.finish_turn`，从用户输入和最终回答提取候选；默认逐条确认，显式自动模式仅自动创建。`MemoryWorkflow.begin_turn` 最多召回五条、最多 20,000 字符正文。`tracecoder/context.py` 原地改写 `agent.messages` 做压缩；`tracecoder/session.py` 主要靠手动 `/save` 保存消息。`tracecoder/tools/todo.py` 的进程内 Todo 被 `Agent._full_messages` 每次完整注入，重启无法恢复；项目级 `TaskStore` 有持久状态，但没有独立验收证据。

因此本设计是替换现有 CLI 的逐轮候选弹窗与整段注入策略，扩展会话持久化和工作状态，不是把 P1 Memory v2 文档描述成已经具有三层能力。现有 `.tracecoder/memory/` 记录、索引和撤销日志保持可读；升级时增加字段或旁路索引，不能静默重写旧数据。旧 `/save`、`--resume`、`remember`、`read_memory`、`list_memories` 入口保留兼容，语义变化在实现时逐项公告和测试。

## 数据所有权与最小接口

1. **SessionJournal**：每个根 CLI 会话一份有序、追加式事件记录，至少包含 `session_id`、绑定的规范化工作区标识、单调 `event_id`、时间、事件类型、作用域和内容/内容引用。记录用户输入、模型最终答复、工具调用及结果、压缩摘要的来源区间、工作卡变更和完成证据。持久化成功后才确认“可恢复”；恢复时校验记录和版本，尾部不完整事件不能被当作成功写入，跨工作区恢复需要明确提示/授权。保留现有会话格式的读取/迁移路径。首版不承诺完整事件重放工具副作用。
2. **WorkState**：每会话一张结构化活动卡，字段为目标、可验证的验收条件、当前步骤、Todo 引用、证据引用、阻碍、下一步、状态和修订号。状态为 `active`、`blocked`、`awaiting_review`、`completed`；`completed` 后标记归档并从默认提示移除，但记录仍可读。只保存工作状态，不重复存整段对话。项目 `TaskStore` 可通过 ID 关联，仍维持自己的任务清单语义。
3. **LongTermMemory**：沿用项目 `.tracecoder/memory/`，另设独立的用户级存储；单条增加来源事件引用、类型、作用域、创建/更新时间、版本和写入方式。首版支持两个作用域，但只把用户直接表达的跨项目偏好/反馈写入用户级，项目事实留在项目级；不能把一个项目事实无提示地升级为用户全局事实。同名时项目级记录只在本项目的检索中优先，不修改用户级原文。
4. **ContextAssembler**：在每次模型请求前以总 token/字符预算组装活动卡、会话近况/摘要和长期索引。提供按稳定引用展开条目及原始证据的路径。它只决定“本次可见什么”，不拥有原始数据，也不修改其来源。现有 Skill 索引和工具权限仍由各自入口提供，不混入记忆排序。
5. **ExtractionQueue**：会话空闲或结束时登记有界的待提取区间和提取版本；同一 `session_id + 事件区间 + 提取版本` 幂等。没有常驻 daemon：CLI 空闲时可处理，正常退出时留下待办，下一次启动重试。辅助提取失败不使主任务失败。

首版文件布局沿用项目 `.tracecoder/memory/` 和现有用户目录 `~/.tracecoder/sessions/`，在后者的 `<id>/` 下新增 `events.jsonl`、`work_state.json` 和待提取队列/索引；用户级长期记忆另存于 `~/.tracecoder/memory/`。具体文件名是实现细节，但必须做到按会话隔离、原子工作卡快照、事件追加与可检测的损坏。大工具输出要有大小上限及受控引用；不能因“保留原始记录”无限制复制二进制或密钥到索引。恢复时报告缺失/截断内容，而不是假装完整。

## 渐进式披露协议

三个层次都使用 `导航 → 摘要 → 原始证据`，而不是“全文默认注入、超限再删”。

| 披露级 | 工作记忆 | 短期记忆 | 长期记忆 |
| --- | --- | --- | --- |
| L0 默认 | 一张活动卡：目标、状态、下一步、关键阻碍/验收摘要 | 近几轮与一份带事件区间的压缩摘要 | 有界的用户/项目索引：名称、类型、短描述、来源标记 |
| L1 相关 | 指定 Todo、验收项、证据摘要 | 命中的旧事件片段/工具结果摘要 | 候选条目的短片段和匹配原因 |
| L2 按需 | 具体工作卡修订及验收证据 | 指定事件/工具原始内容 | 指定记忆正文、历史版本和来源事件 |

L0 必须有独立预算，并给工作卡、最近对话、安全/系统指令及长期索引分配上限；总预算不足时按确定性顺序裁剪可再取回的低优先级内容，并留下稳定引用。不能裁掉仍需配对的工具调用/结果，也不能让记忆正文挤掉当前用户请求。L1/L2 每次展开均有数量和长度上限，结果标注来源、时间与“资料而非指令”。检索无命中时不为了填满预算强塞无关记忆；原始来源不可用时明确提示而不编造。

短期压缩只替换**模型可见视图**：先处理旧且冗长的工具输出，再对旧回合形成有来源区间的摘要。SessionJournal 保留可恢复原始事件或受控截断记录，摘要不得成为唯一事实来源。手动 `/compact` 与自动压缩共用同一规则。

## 写入、自动提取和人工审阅

每轮先持久化新增会话事件与工作卡修订，再组装下一次模型请求。保存失败要向用户明确显示“本轮不可保证恢复”，不能继续以旧工作卡冒充最新状态；主回答已生成时不因辅助记忆失败而丢失。

长期提取不逐轮打断用户：在会话空闲/结束后，按尚未处理的事件区间批量运行，允许**零候选**。只有直接用户表达、可定位的工具/文件证据或用户明确确认的结论可作为事实来源；模型自己的最终回答不能单独证明事实。一次性任务状态、猜测、凭据和大段原文不进入长期记忆。提取候选先去重、校验作用域与来源，再按下面策略处理：

- 新建且有可核对来源、无冲突、无疑似敏感信息的候选可自动保存；写入后在统一记忆视图中可审阅并可撤销。不在每次回答后弹窗。
- 与现有条目相反、要覆盖旧内容、来源不足或疑似敏感的候选进入集中审阅队列；未批准前不成为模型默认可见的长期记忆。确定性敏感匹配直接拒绝保存，不能依靠模型评分放行。
- 内容完全相同或本次无长期价值时不写入；多次启动/重试不得生成重复条目。合并/删除现有条目仍需明确审阅，不因自动模式而直接执行。
- 每次受控写入保留审计和前镜像，撤销前校验版本/哈希；若已有后续修改，拒绝覆盖并请求审阅。显式 `remember` 与自动流水线的权限和审计边界要分开标识。

用户此前选择“自动保存，但提供撤销”，因此本方案对安全的新候选采用自动保存，不继承 P1 的默认逐条确认；敏感、冲突和不确定候选统一审阅。交互 CLI 与 `-p` 采用同一提取/写入规则；`--yes` 仍只影响工具权限，不扩大记忆写入许可。提供显式关停提取/读取的控制，Plan Mode 保持长期记忆只读，不在该模式暗中写入。子 Agent 事件可纳入父会话证据，但只由根会话排队提取，避免重复。

CLI 至少需要统一的记忆状态/待审阅入口、批量审阅、按操作撤销和关闭读取/提取的入口；沿用现有 `/memory undo` 语义，不让用户逐轮回答保存问题。对 `-p` 无交互终端的审阅项只排队，不阻塞命令完成。

## 工作状态、完成与恢复

创建/更新活动卡时要记录验收条件。可机器验证的条件引用检查命令、结果和对应事件；主观条件转 `awaiting_review`，等待用户确认。只有全部必需条件有有效证据、没有未解阻碍，或用户明确确认完成，才迁到 `completed`。模型说“完成了”、Todo 全部 done、停止生成或退出 CLI 均**不是**充分条件。无验收条件时不能自动判定完成；可请用户定义，或保持待审阅。完成后归档活动卡，从 L0 移除，但会话日志、长期记忆和审计/撤销信息按保留策略保存。

`--resume` 从同一 SessionJournal 和最新有效 WorkState 恢复未完成工作；若快照版本落后于事件，重建或提示不一致。`/reset` 不能无提示删除未完成工作：先结束当前上下文/切换会话，保留可恢复状态，并清楚显示如何恢复。一次性 `-p` 也生成可恢复记录；不能因为无交互终端就自动把工作状态标为完成。

## 故障、安全与实现顺序

会话/工作卡写入失败属于恢复保证故障，必须可见；压缩、检索或提取失败属于辅助故障，可以退化到较少上下文并记录原因。队列处理需有幂等键、重试上限和失败状态；退出进程不会神奇完成尚未执行的后台作业。并发写同一会话/同一记忆记录时以版本校验拒绝冲突，不宣称跨进程强事务。记忆、旧会话和工具结果均为低信任资料，不能携带改变权限或系统规则的指令。工作区路径和 Bash/MCP/Hook 执行仍受既有工作区策略约束；本设计不把记忆检索当作沙箱。

实现按可验收切片推进，而不是一次性重写 Agent：

1. 会话事件自动持久化 + WorkState 恢复/归档，保持现有工具和记忆行为兼容。
2. ContextAssembler 与渐进式披露；压缩改为仅修改模型视图，原始记录留存。
3. 空闲/下次启动提取、自动安全写入、集中审阅与撤销；替换 P1 逐轮弹窗。

每片完成后都验证 REPL、`-p`、`--resume`、`--yes`、Plan Mode、`/reset`、`/compact` 和子 Agent 路径的适用行为。关键验收场景：异常退出后恢复最后已确认持久化的工作卡；压缩后仍能按事件引用找回来源；无关长期条目只露索引不载正文；零候选不写入；重试不重复；冲突不覆盖；敏感候选不自动保存；Todo 清空不自动关目标；主观目标待审；完成记录归档但可追溯。以离线测试、Windows 和 Docker/隔离环境结果分别报告，不把静态设计或单平台测试称为真实模型 E2E。

## 与外部机制的关系及持续对照

本方案吸收 [Claude Code 的有界索引/按需主题阅读](https://code.claude.com/docs/en/memory)、[Codex 的空闲后批量提取/允许无结果](https://github.com/openai/codex/blob/main/codex-rs/memories/README.md)、[DeepSeek Harness 的会话事件与模型视图分离](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/compaction.md)，但**不是**任何一家产品的原样实现：TraceCoder 首版没有 Claude Code 的完整 auto-memory 编辑体验，没有 Codex 的全局两阶段整合服务，也没有 DeepSeek Harness 的通用插件式事件运行时。进一步的来源与非等价边界见本工作区的 `原始研究草稿（已移至发布目录外的归档）`，该研究文档不代表 TraceCoder 已实现这些功能。

与用户要求的 `learn-claude-code` 教学仓库对照也需单独保留：其固定提交 `0dcafa2ae053a1ddd6a72f265431104b08a5aa13` 的 `s09_memory` 偏向单回合选取/提取与阈值合并；本方案增加可恢复会话来源、空闲批处理、三层披露和验收式工作状态。教学仓库的 `s10_task_system` 与 `s16_workflow_runtime` 可作为任务/续跑对照，但不等同于官方 Claude Code。每片真正实现后，必须更新 `docs/learn-claude-code-mechanism-comparison.md`，写明来源入口、TraceCoder 实际入口、保留/简化/新增、取舍、测试证据和未实现边界；本文不能代替实现记录。
